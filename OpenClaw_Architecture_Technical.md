## 一、项目概述

### 1.1 什么是 OpenClaw

**OpenClaw** 是一个开源的**本地化 AI 智能助手平台**，运行在企业自有服务器上，通过 WhatsApp、钉钉、微信等通讯工具与用户交互，并能自动操作数据库、浏览器、文件系统等完成复杂任务。

**技术本质**：
- **运行时**：Node.js + TypeScript
- **架构模式**：多进程微服务（Gateway + Agent 分离）
- **存储方案**：SQLite + JSON + 向量数据库
- **AI 集成**：多模型支持（Kimi/Claude/GPT/本地模型）

## 三、分层架构详解

### 3.1 第1层：用户接入层

**功能**：接收来自多平台的消息输入

**支持渠道**：
- WhatsApp Business API
- Telegram Bot API
- Discord Bot
- 钉钉 Webhook
- 企业微信
- Slack Bot
- iMessage
- Email (SMTP/IMAP)

**技术实现**：
```typescript
// 统一消息格式
interface Message {
  id: string;
  from: string;        // 用户ID
  content: string;     // 消息内容
  channel: string;     // whatsapp|telegram|dingtalk
  timestamp: Date;
  attachments?: any[];
}
```

### 3.2 第2层：网关层 (Gateway)

**功能**：统一接入点、身份认证、协议转换、路由分发

**核心组件**：

| 组件 | 技术 | 职责 |
|------|------|------|
| HTTP Server | Express.js | REST API 接口 |
| WebSocket Server | ws | 实时双向通信 |
| Auth Middleware | JWT | Token验证、白名单检查 |
| Channel Adapters | SDK | 各平台协议适配 |
| Message Router | 自研 | 消息路由到对应 Session |

**端口**：默认 18789（本地回环）

**为什么需要 Gateway？**
1. **安全隔离**：只暴露 Gateway，内部服务不直接对外
2. **协议统一**：将各平台不同格式转为统一 Message
3. **进程隔离**：Gateway 独立运行，崩溃不影响核心

### 3.3 第3层：核心服务层

#### Session Manager（会话管理）

**职责**：
- 会话创建、查找、销毁
- 上下文维护（最近 N 轮对话）
- 生命周期管理（超时清理）

**数据结构**：
```typescript
interface Session {
  key: string;              // 会话唯一ID
  userId: string;           // 用户标识
  messages: Message[];      // 历史消息队列
  memory: Memory;           // 记忆数据
  state: object;            // 临时状态
  createdAt: Date;
  updatedAt: Date;
}
```

#### Memory System（记忆系统）

**三层记忆架构**：

```
┌─────────────────────────────────────────────────────┐
│                     记忆系统                          │
├─────────────────────────────────────────────────────┤
│  短期记忆 (Short-term)                                │
│  • 最近 10-20 轮对话                                  │
│  • 存储：内存 (Redis/Memory)                          │
│  • 作用：当前对话上下文                               │
├─────────────────────────────────────────────────────┤
│  长期记忆 (Long-term)                                 │
│  • 用户偏好、历史约定、重要事实                       │
│  • 存储：SQLite                                       │
│  • 作用：跨会话保持个性化                             │
├─────────────────────────────────────────────────────┤
│  语义记忆 (Semantic)                                  │
│  • 向量化存储的历史内容                               │
│  • 存储：向量数据库 (Chroma/Pinecone)                 │
│  • 作用：模糊搜索相关内容                             │
└─────────────────────────────────────────────────────┘
```

#### Cron Scheduler（定时任务）

**功能**：
- Heartbeat 机制：定时轮询检查新消息/邮件/任务
- Cron Jobs：用户配置的定时执行任务
- 任务队列：异步任务调度

**配置示例**：
```json
{
  "name": "daily-report",
  "schedule": "0 9 * * *",
  "task": "查询昨日销售额并发送到微信"
}
```

**处理流程**：

## 四、完整数据流

### 4.1 时序图（以"查询销售额"为例）

```
时间线：

T+0ms      用户在微信发送："今天销售额多少？"
           ↓
T+50ms     微信服务器 → OpenClaw Gateway（Webhook）
           [HTTPS POST]
           ↓
T+100ms    Gateway 层：
           • Token 鉴权（确认是白名单用户）
           • 格式转换（微信格式 → 统一 Message）
           • 路由分发（查找用户 Session）
           ↓
T+200ms    Session Manager：
           • 查找历史 Session
           • 加载记忆（用户是销售总监，关注业绩）
           • 构建上下文（历史5轮 + 当前消息）
           ↓
T+300ms    AI 引擎：
           • 发送给 Kimi API
           • 系统提示："你是企业助手，可查询数据库"
           • AI 推理：意图=查询销售额，工具=query_database
           ↓
T+1500ms   工具层：
           • 权限检查（用户有权访问销售数据）
           • 连接 MySQL 数据库
           • 执行 SQL：SELECT SUM(amount) FROM sales WHERE date = CURDATE()
           • 获取结果：{sales: 150000}
           ↓
T+1800ms   AI 引擎：
           • 接收工具结果
           • 生成回复："今天销售额15万元，比昨天增长12%"
           ↓
T+2500ms   响应层：
           • 格式化（加 emoji、分段）
           • 渠道适配（微信 Markdown）
           ↓
T+2800ms   输出层：
           • 调微信 API 发送消息
           • 用户收到回复
           ↓
T+3000ms   持久层：
           • 保存对话历史到 SQLite
           • 更新记忆（用户关注销售额）
           • 记录审计日志

总耗时：约 3 秒
```

## 五、底层架构详解

### 5.1 Gateway 架构深入

**为什么 Gateway 是核心？**

```
┌─────────────────────────────────────────────┐
│              Gateway (独立进程)              │
│  ┌──────────────┐      ┌──────────────┐    │
│  │  HTTP Server │      │  WS Server   │    │
│  │  Port 18789  │      │  Port 18789  │    │
│  └──────┬───────┘      └──────┬───────┘    │
│         │                      │            │
│         └──────────┬───────────┘            │
│                    ▼                        │
│         ┌──────────────────┐                │
│         │   Auth Router    │                │
│         │  • JWT 验证      │                │
│         │  • 白名单检查    │                │
│         │  • 限流控制      │                │
│         └────────┬─────────┘                │
│                  │                          │
│         ┌────────▼─────────┐                │
│         │  Message Router  │                │
│         │  分发到对应 Agent │                │
│         └────────┬─────────┘                │
│                  │                          │
│                  │ IPC (Unix Socket)        │
└──────────────────┼──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│              Agent (核心进程)                │
└─────────────────────────────────────────────┘
```

**Gateway 职责**：
1. **协议转换**：HTTP/WebSocket → 内部 IPC
2. **安全防护**：只暴露 18789，内部服务不对外
3. **负载均衡**：可对接多个 Agent 实例
4. **心跳检测**：监控 Agent 健康状态

### 5.2 Session 管理机制

**会话查找流程**：

```
收到消息 (userId: "+8618037146353")
    │
    ▼
计算 Session Key (hash(userId + channel))
    │
    ▼
检查内存中是否存在？
    ├── 存在 → 直接返回 Session
    └── 不存在 → 从 SQLite 加载
                    │
                    ▼
            数据库查询 sessions 表
                    │
                    ▼
            加载历史消息（最近20轮）
                    │
                    ▼
            加载用户记忆（偏好、约定）
                    │
                    ▼
            创建 Session 对象，存入内存
```

**Session 生命周期**：

```
创建 → 活跃（接收消息） → 空闲（超时倒计时） → 销毁
 │        │                      │
 │        │                      └── 默认30分钟无消息
 │        │                          保存到数据库，释放内存
 │        │
 │        └── 每次消息重置超时计时器
 │
 └── 新用户首次消息时创建
```

### 5.3 Memory 实现原理

**短期记忆（内存队列）**：

```typescript
class ShortTermMemory {
  private messages: Message[] = [];
  private maxSize = 20;  // 保留最近20轮

  add(message: Message) {
    this.messages.push(message);
    if (this.messages.length > this.maxSize) {
      this.messages.shift();  // 淘汰最早的
    }
  }

  getContext(): Message[] {
    return this.messages;
  }
}
```

**长期记忆（SQLite 存储）**：

```sql
-- 记忆表结构
CREATE TABLE memories (
  id INTEGER PRIMARY KEY,
  user_id TEXT NOT NULL,
  key TEXT NOT NULL,        -- 记忆类型：preference/fact/habit
  value TEXT NOT NULL,      -- 记忆内容
  importance FLOAT,         -- 重要程度（0-1）
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

-- 示例数据
-- user_id="u123", key="preference", value="关注销售额数据"
-- user_id="u123", key="fact", value="公司是SaaS行业"
```

**语义记忆（向量检索）**：

```typescript
// 向量化存储
class SemanticMemory {
  async add(content: string, metadata: object) {
    const embedding = await this.embed(content);  // 生成向量
    await this.vectorDB.insert({
      id: generateId(),
      vector: embedding,
      content: content,
      metadata: metadata
    });
  }

  async search(query: string, topK = 5) {
    const queryEmbedding = await this.embed(query);
    return await this.vectorDB.similaritySearch(queryEmbedding, topK);
  }
}
```

### 5.4 Tools 调用机制

**Tool 定义**：

```typescript
interface Tool {
  name: string;
  description: string;
  parameters: {
    type: "object",
    properties: {
      [key: string]: {
        type: string;
        description: string;
      }
    },
    required: string[]
  };
  execute: (params: any) => Promise<any>;
}

// 示例：数据库查询工具
const queryDBTool: Tool = {
  name: "query_database",
  description: "执行SQL查询数据库",
  parameters: {
    type: "object",
    properties: {
      sql: { type: "string", description: "SQL语句" }
    },
    required: ["sql"]
  },
  execute: async ({sql}) => {
    // 权限检查
    if (!isAllowed(sql)) throw new Error("危险操作");
    // 执行查询
    return await db.query(sql);
  }
};
```

**AI 调用 Tools 的流程**：

```
1. AI 收到用户消息："今天销售额多少？"
   │
2. AI 分析意图：需要查询数据库
   │
3. AI 生成 Tool Call：
   {
     "tool": "query_database",
     "parameters": {
       "sql": "SELECT SUM(amount) FROM sales WHERE date = TODAY()"
     }
   }
   │
4. 系统执行 Tool，获取结果：{sales: 150000}
   │
5. 结果返回给 AI
   │
6. AI 生成最终回复："今天销售额15万元"
```

## 六、核心流程抽象

### 6.1 简化版：三层核心

```
┌─────────────────────────────────────────┐
│  表现层：用户界面（微信/钉钉/邮件）        │
├─────────────────────────────────────────┤
│  接入层：Gateway（统一入口）              │
├─────────────────────────────────────────┤
│  业务层：Session + Memory + Tools         │
├─────────────────────────────────────────┤
│  智能层：AI Provider（多模型支持）        │
├─────────────────────────────────────────┤
│  能力层：Skills（可扩展功能）              │
├─────────────────────────────────────────┤
│  存储层：SQLite + 向量数据库               │
└─────────────────────────────────────────┘
```

### 6.2 流程口诀

**七步流程**：
1. **收** - Gateway 接收消息
2. **记** - Session 加载上下文
3. **想** - AI 理解意图
4. **做** - Tool 执行操作
5. **说** - AI 生成回复
6. **发** - Gateway 发回用户
7. **存** - 保存到数据库

### 6.3 架构设计亮点

| 设计 | 说明 | 价值 |
|------|------|------|
| **Gateway 分离** | Gateway 与 Agent 独立进程 | 稳定性、可扩展 |
| **多 Provider** | 抽象层支持多模型 | 不绑定单一厂商 |
| **三层记忆** | 短期+长期+语义 | 个性化、上下文 |
| **Skills 热插拔** | 动态加载插件 | 易扩展、可定制 |
| **统一消息** | 多平台转为统一格式 | 简化处理逻辑 |
